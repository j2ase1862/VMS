# SW 라이선스 체계 명세 (서명 파일 + 좌석 배분)

문서 버전: v1.0 (2026-08-25, v1.13.0 / Web v1.5.0 기준 — 구현 전 설계 명세)

> 관련 문서:
> - 운영 Web 배포 절차: 멀티 Lot 실증 기록 (memory: project_multilot_field_issues)
> - MSI 구조: `VMS.MasterSetup/Package.wxs`, 릴리즈 절차 `docs/release_manual_procedure.md`
>
> 이 문서는 "라이선스가 무엇을 통제하고, 어디까지 책임지는가"를 정의한다.
> 필드/엔드포인트 상세는 구현 후 코드가 진실이며, 여기서는 **설계 의도와 경계**를 고정한다.

## 1. 한 문장 정의

**라이선스는 "어느 고객이, 몇 대에, 어떤 기능을, 언제까지 쓰는가"의 계약 관리 장치이며,
크래킹 방어 장치가 아니다.**

- 최악의 시나리오는 불법 복제가 아니라 **라이선스 때문에 생산 라인이 서는 것**이다.
  모든 설계 판단에서 "현장 무정지"가 "방어 강도"보다 우선한다.
- .NET 앱은 디컴파일이 쉬우므로 완벽 방어는 목표가 아니다. 통제 지점은 바이너리가 아니라
  **발급(서명 개인키)** 하나로 수렴시킨다.

## 2. 배포·판매 모델 (채택 결정)

| 항목 | 결정 | 근거 |
|---|---|---|
| MSI 배포 | **자유 배포** (필드 엔지니어/테스터/개발자 누구나 다운로드) | 배포와 사용 권한의 분리. MSI에는 비밀이 없다 (ClientApiKey·JWT 키는 현장 생성) — 인앱 업데이트 경로 무수정 |
| 활성화 경로 | **USB 라이선스 파일 단일 경로** — 온라인 활성화 서버는 만들지 않는다 | 파일이 지문 바인딩이라 유출 무해. 인터넷 노출 발급 서버의 운영·보안 비용 > 효익. 오프라인 경로는 어차피 필수이므로 경로를 하나로 통일 |
| 판매 모델 | **영구 라이선스 + 연 유지보수** (만료 시 실행은 유지, 업데이트만 차단) — 권장 기본값 | 만료로 생산이 멈추는 리스크 제거. 구독형(만료 시 실행 차단)은 포맷상 지원하되 기본 아님 |
| 에디션 | 파일 포맷에 `features[]` 자리만 확보, **기능 게이팅 구현은 후속** | 판매 정책 미확정 상태에서 포맷 재발급 사태 방지 |

## 3. 라이선스 파일 포맷

경로: `C:\ProgramData\BODA\VMS\license.lic` (VMS·Web 공용 단일 파일).
`%LocalAppData%`는 Web 서비스 계정이 못 읽으므로 사용 금지.

```json
{
  "payload": {
    "schemaVersion": 1,
    "licenseId": "LIC-2026-0001",          // 발급 대장 키
    "customer": "OO정공",
    "kind": "Production",                   // Production | Internal | Trial
    "edition": "Standard",
    "features": [],                         // 예약: "deeplearning","3d","weldteach"
    "maxClients": 5,                        // 좌석 수 (단일 PC = 1)
    "fingerprint": "A3F2-9K71-BC04-D8E1",   // 바인딩 대상 지문 (Internal은 "*" 허용)
    "issuedAt": "2026-08-25",
    "maintenanceUntil": "2027-08-25",       // 이후 업데이트 차단 (영구+유지보수 모델)
    "expiresAt": null,                      // null=영구. 값 있으면 구독형: 실행 차단
    "keyId": "boda-2026"                    // 서명 키 식별 (rotation 대비)
  },
  "signature": "base64(Ed25519(canonical-json(payload)))"
}
```

- **서명**: Ed25519. 검증은 제품에 내장된 공개키 목록(`keyId` → 공개키)으로 오프라인 수행.
  키 유출 시 새 `keyId`로 발급 전환(rotation) — 기존 발급분은 구 공개키로 계속 유효.
- **canonical JSON**: 서명 대상은 payload의 정규화 직렬화(키 정렬·공백 없음). 직렬화 옵션 차이로
  검증이 깨지는 사고 방지 — 구현 시 VMS/Web/발급 도구가 **같은 정규화 코드를 공유**해야 한다
  (`VMS.Core` 공용 클래스, Web은 프로젝트 참조 불가 시 파일 링크 또는 소스 복제 + 왕복 테스트).
- **kind 구분**:
  - `Production` — 고객 발급분. 지문 필수.
  - `Internal` — 사내(테스터/필드 엔지니어)용. 지문 `"*"` 허용 대신 **만료 90일 필수** (유출 피해 최소화).
  - `Trial` — 데모/평가. `expiresAt` 필수.
- DEBUG 빌드는 검증 생략(개발 마찰 제거). Release 빌드는 항상 검증.

## 4. 하드웨어 지문 (MachineFingerprint)

구성 요소 3종 — ① 레지스트리 `MachineGuid`, ② 주 NIC MAC, ③ CPU ID.

- **2/3 일치 규칙**: 3요소 중 2요소가 맞으면 유효. 공장 PC의 NIC 추가/교체·보드 수리에 대한 관용.
  (구현: 요소별 해시 3개를 라이선스에 넣는 게 아니라, 지문 코드 자체를 요소별 세그먼트로 구성해
  세그먼트 단위 비교 — 상세는 구현 시 확정)
- **표시 포맷**: `XXXX-XXXX-XXXX-XXXX` (16자, Crockford Base32 — 0/O·1/I 혼동 문자 제외).
  **전화로 불러줄 수 있는 길이**가 요구사항이다 (§6 현장 발급 흐름).
- 3요소 모두 바뀐 경우(=PC 교체)는 재발급이 정답이며, 발급 대장에 사유를 기록한다 (§7).

## 5. 배치 시나리오별 검증 흐름

검증 관문은 하나다: **"로컬 `license.lic`이 있으면 그것, 없고 `webServerUrl`이 설정돼 있으면
서버 좌석 임대"** 순서.

### 5a. 단일 PC (VMS + Web 동봉)

`license.lic` 1개 (`maxClients: 1`). VMS와 Web이 같은 파일을 각자 기동 시 검증. 끝.

### 5b. 서버 PC(Web) + 다수 클라이언트 PC(VMS) — 좌석 배분(floating)

- 라이선스 파일은 **Web 서버에만** 설치 (서버 지문 바인딩, `maxClients: N`).
- VMS 클라이언트는 기동 시 서버에서 **좌석 토큰을 임대(lease)**하고, 기존 `HeartbeatService`
  주기에 편승해 갱신한다. 새 통신 채널을 만들지 않는다.
- 좌석 토큰: 서버가 서명한 단기 토큰(**유효 72시간**), 클라이언트가 로컬 캐시.
  → **서버 다운 시 72시간 유예 운전** — 라이선스 문제로 라인이 서지 않게 하는 핵심 장치.
- 좌석 점유 키는 기존 `ClientIndex` + 클라이언트 지문. 좌석 만석 시 신규 클라이언트는
  기동 차단이 아니라 **경고 + 서버 관리 화면에 초과 표시** (§9 전환 정책과 동일 사상 —
  차단은 좌석 회계가 안정화된 후 후속 결정).
- 클라이언트 PC 교체 시 재발급 불필요 (서버만 바인딩) — B-1(클라이언트별 개별 발급) 대비
  이 방식을 채택한 핵심 이유.

### 5c. 단독 VMS (Web 미사용 현장)

5a와 동일하게 로컬 `license.lic` (`maxClients: 1`). 검증 관문의 폴백 순서로 자연 처리.

### 상태 전이 (영구+유지보수 모델 기준)

| 상태 | 조건 | 동작 |
|---|---|---|
| 정상 | 서명·지문 유효 | 무표시 |
| 유지보수 만료 임박 | `maintenanceUntil` 30일 전 | 기동 시 비차단 경고 (StartupHealthCheck → 감사로그) |
| 유지보수 만료 | `maintenanceUntil` 경과 | **실행 유지**, 인앱 업데이트만 차단 + 경고 |
| 구독 만료 임박 | `expiresAt` 30일 전 | 비차단 경고 |
| 구독 만료 | `expiresAt` 경과 | **유예 14일** (매 기동 경고) → 이후 기동 차단 |
| 라이선스 없음/서명 불일치 | — | 전환기: 경고만 (§9). 최종: 기동 차단 (MessageBox + Shutdown) |
| 지문 불일치 (2/3 미달) | — | 기동 차단 + 지문 코드 표시 (재발급 유도) |

- 시계 되돌리기 방어는 **최소한만**: 마지막 실행 시각을 기록하고 역행 감지 시 경고.
  차단까지는 하지 않는다 (현장 PC 시계 오설정은 흔한 정상 상황).

## 6. 발급·활성화 운영 흐름 (USB 단일 경로)

| 경우 | 흐름 |
|---|---|
| **사전 스테이징** (자사에서 PC 세팅 후 출하 — 대부분) | 사내에서 지문 확인 → 발급 → `license.lic` 설치 → 출하. 현장 작업 없음 |
| **현장 발급** (고객 준비 PC) | 설치 → AppSetup이 지문 코드 표시 → 전화/메신저로 본사 전달 → 발급 → 엔지니어 휴대폰으로 파일 수신 → USB → 현장 PC 복사 |
| **사내(테스터/개발)** | Internal 라이선스(지문 `"*"`, 만료 90일) 공용 사용. DEBUG 빌드는 검증 없음 |

AppSetup 요구사항 (활성화 UI는 MSI가 아니라 AppSetup 담당 — 기존 "MSI는 설치, 구성은 마법사" 원칙):

- 지문 코드 표시 + 클립보드 복사 버튼
- "라이선스 파일 가져오기": 파일 선택 → 서명·지문 검증 → `C:\ProgramData\BODA\VMS\license.lic` 배치
  (ProgramData 쓰기는 기존 `--apply-web-config` UAC 상승 경로 재사용)
- 현재 라이선스 상태 카드 (고객명·에디션·좌석·만료)

## 7. 발급 도구 (사내 전용, LicGen)

**필요하다** — 서명 연산과 포맷 정합성은 수작업 불가. 단, 서버가 아니라 소형 사내 도구다.

- **형태**: 소형 WPF 앱 (발급 담당자가 비개발자일 수 있음). 입력: 지문·고객·kind·에디션·
  maxClients·만료일 → 출력: `license.lic`.
- **발급 대장 내장**: 모든 발급·재발급을 SQLite 한 파일에 자동 기록
  (licenseId·고객·조건·발급자·일시·재발급 사유). **라이선스의 본래 목적이 계약 관리이므로
  대장이 도구의 절반이다.** 재발급(PC 교체) 이력 추적 근거.
- **배포 통제**: MSI에 절대 동봉하지 않는다. 리포 분리(별도 사내 리포 권장) 또는 배포 제외 경로.
  **개인키가 전체 체계의 급소** — DPAPI 또는 암호 보호, `keyId` 기반 rotation 절차 문서화.
- 발급 권한자는 지정 인원으로 한정 (도구+키 보유 = 무제한 발급 가능이므로).

## 9. 단계적 전환 (기존 현장 보호)

이미 v1.13.0까지 배포된 현장이 있으므로, 라이선스 도입 버전으로 업데이트 시 차단되면 사고다.

| 단계 | 릴리즈 | 동작 |
|---|---|---|
| 1. 호환 모드 | 도입 릴리즈 ~ +1 | 라이선스 없음 = **경고만** (기동 시 상태바/로그). 이 기간에 기존 현장 전수 발급 |
| 2. 강제 모드 | 이후 릴리즈 | 라이선스 없음 = 기동 차단. 전환은 릴리즈 노트에 명시 |

- `ClientApiKeyOptions.Required=false` 호환 모드와 동일한 선례.
- 좌석 초과 차단(§5b)도 같은 사상으로 "경고 → 후속 결정" 순서를 따른다.

## 10. 명시적 비범위

- **온라인 활성화 서버** — 만들지 않는다 (§2).
- **NativeVision(C++) 내 검증** — 초기 버전 생략. 크래킹 난이도 향상 필요가 실제로 생기면 후속.
- **강한 시계 조작 방어 / 난독화** — 하지 않는다 (§1의 목적 정의에 따라).
- **기능별 게이팅 구현** — 포맷 예약만 (§2). 판매 정책 확정 후.
- **좌석 실시간 회수/이관 UI** — 초기엔 72h 토큰 자연 만료로 충분. 필요 시 Web 관리 화면 후속.

## 11. 열린 결정 사항

1. 판매 모델 기본값(영구+유지보수)은 권장안 채택 상태 — **영업 정책으로 최종 확정 필요**.
2. 좌석 만석 시 신규 클라이언트 차단 여부 (현재: 경고+표시만) — 강제 모드 전환 시 재논의.
3. 발급 도구 리포 위치·발급 권한자 지정 — 조직 결정.
