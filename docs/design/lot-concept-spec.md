# Lot 개념·구현 의도 명세 (WO–Lot 이중 축)

문서 버전: v1.0 (2026-08-21, v1.13.0 / Web v1.5.0 기준)

> 관련 문서:
> - 혼합 레시피 작업지시: [wo-mixed-recipe-spec.md](wo-mixed-recipe-spec.md)
> - 멀티 Lot 병행 운용 구현: VMS PR #352 + Web PR #80 (v1.11.0), 현장 실증 후속 VMS #356 + Web #82~#85 (v1.13.0)
>
> 이 문서는 "Lot이 무엇을 위해 존재하고, 어디까지 책임지는가"를 정의한다.
> 필드/엔드포인트 상세는 코드가 진실이며, 여기서는 **설계 의도와 경계**만 고정한다.

## 1. 한 문장 정의

**WO(작업지시)는 "얼마나 만들 것인가"의 축(계획·진행·완료)이고,
Lot은 "이 제품들이 어떤 묶음으로 생산됐는가"의 축(추적성·품질 이력)이다.**

두 축은 의도적으로 분리되어 있으며, 서로의 판정에 관여하지 않는다.

## 2. 왜 분리했는가

| 질문 | 담당 축 | 근거 데이터 |
|---|---|---|
| 계획 대비 몇 개 만들었나, 언제 끝나나 | WO | `WorkOrder.Produced/Pass/NgQuantity` + 레시피 라인(WorkOrderItem) |
| 이 불량은 어느 생산 묶음에서 나왔나 | Lot | `Lot.Quantity/PassCount/NgCount` + `InspectionHistory.LotId` + NG 이미지 메타 |

- 수량 집계를 추적성에 묶으면, 추적 정보가 빠졌을 때 **생산 진행 자체가 멈춘다** —
  반대로 추적성을 집계에 묶으면, 집계 편의 때문에 묶음 구분이 왜곡된다.
- 그래서 **집계(WO)는 강제, 귀속(Lot)은 best-effort**로 설계했다 (§6).
- 추적성 표준(IATF 16949, ISO 9001)의 "검사 결과의 로트 귀속" 요구는 Lot 축이 담당한다.

## 3. 데이터 모델과 수명

```
WorkOrder 1 ──── * Lot (Open/Closed)
    │                │
    │ (수량 집계)      │ (귀속)
    ▼                ▼
Produced/Pass/Ng   InspectionHistory.LotId ── NG 이미지 메타 Lot
+ WorkOrderItem    Lot.Quantity/PassCount/NgCount
```

- **발행/마감은 Web 전용** (`POST /api/workorders/{id}/lots`, `POST /api/lots/{id}/close`).
  WO가 Closed만 아니면 발행 가능(Planned 포함), **동시 Open 개수 제한 없음**.
- LotNumber 채번: `{YYYYMMDD}-{OrderNo}-{Sequence:D3}` — 같은 WO 안에서 Sequence 증가.
- 나누는 기준(자재 롯트/시간대/교대 등)은 시스템이 정하지 않는다 — **현장 운영의 결정**이고,
  시스템은 그 결정을 기록·귀속할 뿐이다.

## 4. 흐름: 사이클 1회가 남기는 것

VMS는 검사 사이클 업로드(`POST /api/parameters/results`)에 `WorkOrderId` + `LotId`(선택된 Lot)를 첨부한다.
서버는 한 요청으로 **세 가지를 독립적으로** 갱신한다:

1. **WO 카운터** — `workOrderId` 기준. 레시피 라인 귀속(미스매치면 전체 스킵 = 수량 오염 방지),
   계획 도달 시 자동 완료, `WorkOrderUpdated` 브로드캐스트.
2. **Lot 카운터** — `lotId` 기준, WO와 완전 독립. Lot을 여러 개로 나눠도 WO 합계는 동일.
3. **검사 이력 귀속** — `InspectionHistory.WorkOrderId/LotId` 저장 → 생산 이력의 WO/LOT 필터(Web #85)와
   Excel 내보내기, NG 이미지 메타의 근거.

**의도적 비대칭**: WO 완료 판정에 Lot 카운터는 쓰이지 않고, Lot에는 "계획 수량" 개념이 없다
(Lot.Quantity는 실적 누계). Lot 마감은 완료가 아니라 **묶음의 종료 선언**이다.

## 5. 멀티 Lot 병행과 작업자 선택 (v1.11.0~)

한 WO에 Open Lot이 여러 개면 "지금 라인에 흐르는 물량이 어느 묶음인지"는 **현장만 안다**.
그래서 시스템이 추측하지 않고 작업자가 헤더 Lot 콤보에서 직접 선택한다.

선택 정책 (`MainViewModel.ResolveLotSelection`):

| 상황 | 동작 |
|---|---|
| 현재 선택 Lot이 목록에 남아 있음 | **유지** (갱신 노이즈에 선택이 튀지 않게) |
| 선택 없음 + Open 1개 | **자동 선택** (단일 Lot 운용은 무개입) |
| 선택 없음 + Open 여러 개 | **비움 + 작업자 선택 대기** (경고 로그) |
| 선택 Lot 마감됨 | 목록에서 제거 → 위 규칙 재적용 |

- 동기화: Web 발행/마감 시 SignalR 푸시(`LotIssued`/`LotClosed`, `/hubs/vms-public`) + 60초 폴링 안전망.
- 콤보는 **어떤 해상도에서도 항상 노출** (#356) — 멀티 Lot에선 필수 UI이므로 컴팩트 헤더 숨김 대상이 아니다
  (2026-08-21 실증에서 FHD 숨김이 Lot 미선택 사고로 이어진 교훈).

## 6. Lot 미선택 시의 동작 — 정책 결정 사항

**현재 정책: 비강제.** Lot 미선택이어도 운전·업로드는 진행되고 `LotId=null`로 나간다.
- 결과: WO 집계는 정상, **Lot 귀속만 조용히 빠진다** (이력의 WO/LOT 열에 `—`).
- 근거: 수량 집계(계획 달성)는 생산의 필수 기능, 추적성은 라인 사정에 따라 없을 수 있는 부가 축.
  Lot 없는 스탠드얼론/오프라인 운용도 막지 않는다.
- **트레이드오프**: 추적성이 계약 요건인 현장에서는 미선택 운전이 곧 기록 공백이다.
  강제(미선택 시 운전 차단 또는 경고 다이얼로그)로 바꿀지는 **현장 요구 확인 후 결정** — 바꾼다면
  운전 시작 게이트(`CanStartStop`)에 조건을 추가하는 지점이 된다.

## 7. 다른 개념과의 관계

- **혼합 레시피 라인(WorkOrderItem)과 직교**: 라인은 "무엇을(레시피별) 얼마나"의 세분화,
  Lot은 "언제/어떤 묶음으로"의 세분화. 한 사이클은 (RecipeId→라인 귀속) + (LotId→Lot 귀속)을 동시에 갖는다.
- **Phase B(Barcode/RFID 개체 추적)의 토대**: 개체(시리얼) 단위 추적은 Lot(묶음) 아래에 증축한다 —
  Lot 없이 개체 추적만 있는 구조는 만들지 않는다. (S/N 입력칸은 이미 사이클 업로드에 동봉됨)
- **레거시 데이터**: WO/Lot 도입 전 업로드 행은 `InspectionHistory.WorkOrderId/LotId = NULL`.
  필터 적용 시 제외되는 것이 올바른 동작이며, "미지정만 보기" 옵션은 수요 확인 후 추가.

## 8. 운영 주의 (현장 안내용 요약)

1. Open Lot이 2개 이상이면 **헤더 Lot 콤보에서 반드시 선택** — 선택 없이 운전하면 수량은 올라가도
   Lot별 품질 이력이 비게 된다.
2. Lot 마감은 Web에서 — VMS 콤보는 수 초 내(늦어도 60초) 따라온다.
3. 생산 이력에서 Lot 단위 조회: 작업지시 선택 → LOT 선택 (Web v1.5.0~). Excel에도 WO/Lot 열 포함.
4. Lot을 몇 개로 나눌지는 운영 결정 — 시스템 제한 없음. 다만 너무 잘게 나누면 작업자 전환 조작이 늘어난다.
